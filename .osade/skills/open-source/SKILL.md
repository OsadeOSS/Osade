# Open Source Contribution Skill

## Purpose

* Make open-source contributions minimal, focused, easy to review, and easy to merge.

## Core Rules

1. **Make the Smallest Possible Change** — Change only what is necessary to solve the issue; avoid unrelated refactoring, formatting, renaming, or abstractions.
2. **One Issue = One Branch** — Create a fresh branch from the appropriate base branch for every new issue and never mix unrelated work.
3. **Respect Repository Conventions** — Read `CONTRIBUTING.md`, `README.md`, `.github/`, `AGENTS.md`, `CLAUDE.md`, and follow the project's existing conventions.
4. **Learn From Accepted Contributions** — When expectations are unclear, inspect recent merged PRs, closed issues, and similar changes before guessing.
5. **Stay Within Issue Scope** — Treat the issue and maintainer comments as the boundary and avoid fixing unrelated problems.
6. **Test the Change** — Run the smallest relevant tests, linters, type checks, builds, or other verification needed to validate the fix.
7. **Review the Diff** — Remove accidental formatting, debug code, temporary files, generated files, unnecessary dependencies, and unrelated changes.
8. **Keep PRs Focused** — Clearly state the problem, solution, verification, and related issue while following the repository's PR template and conventions.
9. **No Coding-Agent Attribution** — Never mention or add attribution for Claude, Codex, Cursor, AI assistants, or other coding agents in contributions.
10. **Do Not Invent Information** — Never fabricate test results, issue numbers, benchmarks, approvals, compatibility claims, links, or implementation behavior.
11. **Follow the Contribution Workflow** — Understand the issue, inspect conventions and code, determine the minimal fix, create a branch, implement, test, review the diff, and prepare the PR.
12. **Optimize for Maintainers** — Prefer the implementation with less change, complexity, and review burden when multiple correct approaches exist.

# Additional Contribution Rules

12. **Keep Commit Messages Short** — Use a concise one-line commit message that describes the change; put detailed context in the PR description or comments instead.
13. **Keep PR Comments Concise** — When responding to maintainer feedback, write a short, direct comment explaining what was changed or why, rather than a long explanation.
14. **Do Not Overwrite Maintainer Discussion** — Address maintainer feedback with a focused comment and make only the changes necessary to resolve the feedback.
15. **No Author Attribution** — Never add "Authored by Claude", "Authored by Codex", "Generated by AI", or any similar coding-agent attribution.
16. **Avoid Artificially Detailed Commits** — Do not write long, multi-paragraph commit messages or excessive commit history for small changes.
17. **Use Natural Contribution Language** — PRs, commits, comments, and documentation should be concise and read like normal developer-written contributions.
18. **Never Use Em Dashes** — Do not use the em dash character (`—`) in commits, PRs, comments, documentation, or other contribution text.


## Core Principle

* **Problem → Minimal Fix → Verification** — Every contribution should tell a simple story that a maintainer can understand and review quickly.
